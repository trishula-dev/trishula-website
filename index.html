Trishula moves web application and API protection to kernel altitude on Kubernetes: an eBPF shield drops what must be dropped in the packet path, a userspace engine runs the full detection stack you already trust — OWASP CRS, CEL rules, positive security from OpenAPI, bot detection — and a Kubernetes-native control plane ties policy, rollouts and verdict telemetry together. Decisions land in OpenTelemetry, not syslog.

Why Trishula

Three curves are converging

Kubernetes ingress is consolidating onto the Gateway API; eBPF has matured into a dependable platform for kernel-altitude packet processing; and AI-generated traffic — agents, scrapers, automated abuse — is arriving at exactly the layer the WAF inspects. Each alone is an optimization. Together they are a new opening.

Adoptability is a feature

Negative signatures alone cannot carry a modern estate: too much good traffic to miss, too slow to maintain by hand. Trishula is built developer-first — CRD-driven policy, per-route promotion gates from learn to shadow to enforce, and honest, verifiable verdict telemetry — so the people who own the app can own its protection.

Full detection stack, kernel altitude

Most WAFs give you one plane. Trishula pairs a bounded, fail-open-by-default eBPF shield with the complete detection stack in userspace — you keep the detection quality of a real WAF and gain a kernel-altitude enforcement point that a plain middleware chain can never offer.

How it works

Three components, two planes, one decision record per request.

kernel shield

An XDP/TC eBPF program: L3/L4 ACLs, a verdict cache and a ban table with TC_ACT_SHOT drops, plus flow events streamed to userspace over a ring buffer. Parsing is bounded and tail-call bounded, verifier-verified in CI. Pre-cleared flows never pay userspace cost.

userspace engine

The detection ladder: S0 kernel pre-clear → S1 verdict cache → S2 CEL rules → S3 OWASP CRS via embedded Coraza → S4 positive security (OpenAPI 3.1) → S6 bot detection (JA4, header behaviour). Short-circuit ordering; every verdict recorded.

control plane

WAFPolicy and BanPolicy CRDs compiled to engine bundles and shield maps. Installed behind the Gateway API — NGF as the reference data plane — steering to the engine as a plain backend. Rollback is a CRD re-pin, never a hand-hack.

How it's different

Coraza, ModSecurity, SafeLine, open-appsec, CrowdSec, fail2ban — each earns its keep, and Trishula borrows deliberately from them. What nobody yet occupies is the quadrant where the full detection stack meets Kubernetes-native operations and a kernel-altitude enforcement point. Trishula is built to hold that quadrant:

  • Parity, not a rewrite — CRS runs via embedded Coraza as the reference evaluator, with a CI-blocking differential suite proving the engine matches it.
  • Positive security from day one — OpenAPI-derived route invariants with learn → shadow → enforce promotion gates.
  • Bot mechanisms, not just signatures — JA4 fingerprints, header-order and behavioural windows feeding an evidence-recorded ban engine.
  • ScoredWindowBan — fail2ban-style behaviour bans with an algorithmic scoring window, prefix escalation off by default, every ban carrying evidence.
  • Telemetry as a contract — every verdict is a correlated OpenTelemetry span + metric + log; dashboards ship in-repo.
  • Crowdsourced rules — CEL rule packs and shared intel start in-repo and graduate upstream as the community forms.

Status & roadmap

Pre-alpha. The kernel shield, userspace engine and operator are being built in the open, sprint by sprint. Work is tracked as issues labeled by target window — the board below aggregates them.

now
PoC ladder — XDP/TC shield PoC, ringbuf ingest, HTTP/1 + detection ladder slice, CEL rules, CRS differential in shadow, CRD round-trip, NGF steering lab.
next
Depth — HTTP/2/gRPC reconstruction, Vectorscan hot path, CEL hot reload, OpenAPI learn mode, behavioural bot v1, the full rate-limit ladder, ONNX scorer, bench harness to the latency/throughput targets.
later
Community & reach — academy labs, HTTP/3 posture evaluation, behavioural DoS detectors, DPU evaluation, multi-arch builds, uninstall residue gate.
